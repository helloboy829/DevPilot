## 复发时的安全恢复顺序

### 1. 先区分应用故障与 Docker 故障

使用当前 Docker Desktop CLI 的 `--help` 核对版本支持。限时检查 `docker info`、`docker ps` 和目标容器状态；登录页可达不证明管理接口可用，也不证明新版已部署。

若引擎正常而仅一个应用失败，只调查对应服务；不要以重启整个 Docker 代替应用诊断。若 Desktop/API 无响应，先记录现象与时间，不循环启动多个挂起客户端。

### 2. 有明确授权才重启

重启 Docker 会短暂影响本机其他容器，必须先说明影响。优先普通重启：

```powershell
docker desktop restart --timeout 120
```

仅在普通退出失败且获得明确授权时，再执行官方强制停止/启动：

```powershell
docker desktop stop --force --timeout 90
# 只有停止成功后才启动；失败时先调查，不盲目继续。
if ($LASTEXITCODE -eq 0) { docker desktop start --timeout 180 }
```

强制停止可能打断在途写入；不删除卷不等于数据天然完整。因此恢复后必须核对数据库完整性、既有记录及服务状态，不能只看命令退出码。不能承诺未知在途请求未执行；评测的未知送达仍不自动重试。

严禁顺手执行 `docker compose down -v`、卷删除、`docker system prune`、恢复出厂设置、WSL unregister 或全局 WSL shutdown。清理系统磁盘/旧镜像、修改内存限制及重启其他应用，都属于独立操作，不能从重启授权推导。

### 3. 恢复后再做应用升级

1. 核对引擎就绪与原容器状态；不要自动启动原本已停止的无关容器。
2. 将部署清单固定到完整 Git SHA；比对当前容器代码与提交，确保清单完整。构建上下文仅允许审核过的源码，不包含配置/密钥/材料/数据库。
3. 记录配置文件哈希、挂载、容器身份和迁移版本，不把真实值上传。制作并校验在线一致性备份，保留原镜像与原 Compose。
4. 使用同一 Compose project，仅更新 gateway/frontend，保留原卷、配置和依赖服务。不要运行破坏性 down。
5. 复核账号、旧数据、两套 ledger、完整性、外键、配置哈希、挂载及无关容器身份；比对容器源码哈希，确认健康与登录/API边界。只读冒烟不保存业务对象或外呼。
6. 将脱敏的结果与边界同步至进度文档；原始证据、备份、token、用户信息与真实配置只留在本地私有目录/卷。CI 必须核对对应完整 SHA，不以历史绿灯或 HTTP 200 代替。
7. **每次成功升级都执行镜像维护收尾**：按[镜像清理与空间维护](DevPilot_Docker_Diagnostics.md#镜像清理与空间维护)核对全部容器引用（包括已停止容器），精确删除已确认归属 DevPilot、无引用且不再需要的旧镜像和中间版本，随后再查服务健康。验收前不能删除回退镜像；升级失败则保留恢复依据。不要为了删镜像顺手删除停止容器或数据卷；未知归属或仍被引用的镜像保留并说明原因。

本次私有部署助手是针对当时镜像/挂载/迁移审核的操作记录，不是可跨环境直接运行的公共部署工具。不要复制私有运行文件进仓库。

## 回退边界

若尚未迁移，保留旧镜像与原配置可为人工回退提供依据。一旦数据库已追加迁移，不能直接用旧镜像覆盖或自动降级 ledger。应先停止新增业务写入，确认是否有更新后的合法数据，再审核恢复计划；从备份恢复可能丢失备份之后的数据，需要单独确认。不要自动覆盖当前库、复用未知结果的执行 ID 或重试未知目标请求。

## 前端构建与运行分离

仓库生产 Dockerfile 原本已经在 builder 阶段预构建，但本地私有 Compose 的启动覆盖仍会重复编译。两者须分开核对，不能只检查仓库默认配置。

本轮生产镜像约定：

- builder 阶段安装锁定依赖并编译；运行阶段只复制产物，不再重复下载/安装 Corepack、pnpm。
- 运行工作目录为 `/app/frontend`，`NODE_ENV=production`，通过 exec 形式的 Node 命令启动 `next start`，明确监听容器内 `0.0.0.0:3000`，不增加宿主机发布端口。
- Node 直接作为应用进程接收停止信号；若部署启用了 Docker init，则由 init 转发，不经过额外的 shell / pnpm 启动包装。开发 `dev` target 仍保留热更新；开发者 `preview` 命令仍是手工构建后预览，不作为生产启动方式。
- `backend/tests/test_frontend_docker_runtime.py` 先红后绿验证直接启动、构建/运行阶段边界、生产 Compose 不覆盖命令、开发模式不回退。配置测试不是完整生产镜像构建测试。
- 本地替换应使用代码专用上下文、现有锁定依赖和不含真实 `.env` 的静态镜像，而不是 `docker commit` 抓取运行容器。先保存私有 Compose 与配置/挂载/账号/评测数据的校验收据，仅重建 frontend；gateway、数据库、其他项目都不重建。待前端就绪后重载原 nginx。
- 重启验证必须比较构建 ID 与构建清单哈希，并检查实际主进程和页面可用性；不能只看容器为 running。运行时注入的私有前端配置继续只读挂载，不复制到构建上下文。`NEXT_PUBLIC_*` 是构建期配置：其变更必须显式重建镜像，不能承诺仅重启就生效。

本地已完成：使用现有静态依赖镜像离线构建，检查其不含真实前端环境文件；仅替换 frontend，并保留原有 Docker init、配置及挂载。一次仅前端重启后，构建 ID 与四份构建清单哈希未变化，确认没有重新编译；入口及所有既有账号的助手/报告页只读冒烟通过，无浏览器错误、业务写入或模型/目标调用。账号、评测数据与迁移 ledger 的只读校验收据保持一致，其他容器身份未变化。运行配置、备份与收据仅留在本地 gitignored 目录，不随代码提交。首次进程校验因误以为 Node 必须是 PID 1 而失败；确认原配置本就启用 Docker init 后改为验证 init 的直接 Node 子进程，未关闭 init 或改动其他服务。

该改进消除重复启动构建，不消除首次镜像构建的资源峰值，也不保证 Docker Desktop 永不复发。镜像构建应避开正在执行的评测，不在构建或启动阶段自动删除回退镜像、扩大系统资源或重启整个引擎。遵循用户已明确要求的维护规则：升级验收成功后定向清理无容器引用的旧 DevPilot 镜像，不能用全局 prune 代替。

## 复发原因与后续改进

有限日志扫描看到管理 IPC deadline，扫描范围内没有 OOM/磁盘耗尽特征；恢复时本机可用内存、系统盘空间偏紧。这些只能作为调查线索，尚不能确定根因。没有进行全盘日志/性能归因审计，也不能保证重启后不再发生。

本地实例实际使用生产模式，但此前在每次容器启动时都重新执行 `build && start`，并非开发服务器热更新。该重复构建会增加启动期资源开销，但目前没有证据证明它就是 Docker 管理接口卡死的根因。

后续应分别评估：主机可用资源、Docker Desktop 日志/磁盘增长、应用自身健康检查和有界诊断。不要自动扩大资源、清理磁盘或升级 Docker；先给出影响与验证方案。此次未加入自动重启/自动重试，避免打断评测、模型请求或其他项目。

本记录不代表实际 Office 排版验收、真实模型/目标联调、正式报告批准、调度准入或整个平台完成；这些仍需对应功能和测试。
