## 复发时的安全恢复顺序

### 1. 先区分应用故障与 Docker 故障

使用当前 Docker Desktop CLI 的 `--help` 核对版本支持。限时检查 `docker info`、`docker ps` 和目标容器状态；登录页可达不证明管理接口可用，也不证明新版已部署。

若引擎正常而仅一个应用失败，只调查对应服务；不要以重启整个 Docker 代替应用诊断。若 Desktop/API 无响应，先记录现象与时间，不循环启动多个挂起客户端。

### 2. 有明确授权才重启

重启 Docker 会短暂影响本机其他容器，必须先说明影响。优先普通重启：

```powershell
docker desktop restart --timeout 120
```

仅在普通退出失败且获得明确授权时，再执行官方强制停止/启动：

```powershell
docker desktop stop --force --timeout 90
# 只有停止成功后才启动；失败时先调查，不盲目继续。
if ($LASTEXITCODE -eq 0) { docker desktop start --timeout 180 }
```

强制停止可能打断在途写入；不删除卷不等于数据天然完整。因此恢复后必须核对数据库完整性、既有记录及服务状态，不能只看命令退出码。不能承诺未知在途请求未执行；评测的未知送达仍不自动重试。

严禁顺手执行 `docker compose down -v`、卷删除、`docker system prune`、恢复出厂设置、WSL unregister 或全局 WSL shutdown。清理系统磁盘/旧镜像、修改内存限制及重启其他应用，都属于独立操作，不能从重启授权推导。

### 3. 恢复后再做应用升级

1. 核对引擎就绪与原容器状态；不要自动启动原本已停止的无关容器。
2. 将部署清单固定到完整 Git SHA；比对当前容器代码与提交，确保清单完整。构建上下文仅允许审核过的源码，不包含配置/密钥/材料/数据库。
3. 记录配置文件哈希、挂载、容器身份和迁移版本，不把真实值上传。制作并校验在线一致性备份，保留原镜像与原 Compose。
4. 使用同一 Compose project，仅更新 gateway/frontend，保留原卷、配置和依赖服务。不要运行破坏性 down。
5. 复核账号、旧数据、两套 ledger、完整性、外键、配置哈希、挂载及无关容器身份；比对容器源码哈希，确认健康与登录/API边界。只读冒烟不保存业务对象或外呼。
6. 将脱敏的结果与边界同步至进度文档；原始证据、备份、token、用户信息与真实配置只留在本地私有目录/卷。CI 必须核对对应完整 SHA，不以历史绿灯或 HTTP 200 代替。

本次私有部署助手是针对当时镜像/挂载/迁移审核的操作记录，不是可跨环境直接运行的公共部署工具。不要复制私有运行文件进仓库。

## 回退边界

若尚未迁移，保留旧镜像与原配置可为人工回退提供依据。一旦数据库已追加迁移，不能直接用旧镜像覆盖或自动降级 ledger。应先停止新增业务写入，确认是否有更新后的合法数据，再审核恢复计划；从备份恢复可能丢失备份之后的数据，需要单独确认。不要自动覆盖当前库、复用未知结果的执行 ID 或重试未知目标请求。

## 复发原因与后续改进

有限日志扫描看到管理 IPC deadline，扫描范围内没有 OOM/磁盘耗尽特征；恢复时本机可用内存、系统盘空间偏紧。这些只能作为调查线索，尚不能确定根因。没有进行全盘日志/性能归因审计，也不能保证重启后不再发生。

后续应分别评估：前端开发服务器编译峰值与生产构建运行方式、主机可用资源、Docker Desktop 日志/磁盘增长、应用自身健康检查和有界诊断。不要自动扩大资源、清理磁盘或升级 Docker；先给出影响与验证方案。此次未加入自动重启/自动重试，避免打断评测、模型请求或其他项目。
