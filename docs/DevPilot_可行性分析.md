# DevPilot 可行性分析 v1.0

## 0. 文档说明

**目的**：在投入研发前，从市场、技术、经济、运营、合规五个维度评估 DevPilot 的可行性，确定产品定位、边界与立项结论。

**结论摘要**：**可行**。采用「个人开发者 / 小团队 + SaaS 云服务 + 国产模型为主」的定位。最大技术风险是代码执行沙箱的安全隔离，最大经济风险是 LLM 成本失控，两者均需在正式立项前通过 PoC 验证。

## 1. 产品定位

### 1.1 一句话定位

面向个人开发者与小团队的 **SaaS 多智能体研发协同平台**：输入自然语言需求，自动完成「需求分析 → 设计 → 编码 → 测试 → 评估 → 报告」的完整研发闭环。

### 1.2 目标用户

- 个人独立开发者 / 自由职业者
- 3-10 人小团队（创业团队、外包小组、学生项目组）
- 核心痛点：研发人力不足、重复性编码、缺少自动化测试与质量评估手段

### 1.3 非目标用户（明确不做）

- 大型企业（私有化、企业权限体系、合规审计、SSO 等）—— 列为后续扩展方向，不进入首版范围
- 需求高度定制化的行业客户

## 2. 市场与竞争分析

### 2.1 市场背景

Agentic 编程（AI Agent 辅助/代替写代码）是当前开发者工具增长最快的方向。市场已从「代码补全」（Copilot/Cursor）演进到「任务级自动化」（Copilot Workspace / Devin）。

### 2.2 竞品分析

| 竞品 | 形态 | 优势 | 差距 / 机会 |
| --- | --- | --- | --- |
| Cursor | 编辑器插件 | 交互式编码体验 | 不覆盖完整研发流程 |
| GitHub Copilot Workspace | 任务式（issue→PR） | GitHub 深度集成 | 偏改动既有代码库 |
| 通义灵码 / CodeGeeX | 编辑器插件 | 国产、低成本 | 以代码补全为主 |
| Devin | 全自动研发 Agent | 全自动闭环 | 企业向、价格高 |
| **DevPilot** | **全流程 SaaS** | **设计→编码→测试→评估闭环、轻量低价** | 全新赛道切入 |

### 2.3 差异化机会

- **完整研发闭环**：不只写代码，还自动做设计、测试、评估、交付报告
- **轻量 SaaS**：无需安装 IDE 插件，Web 即用，低门槛
- **成本优势**：国产模型为主 + 模型路由，边际成本远低于海外全自动产品

## 3. 技术可行性

### 3.1 技术成熟度评估

| 模块 | 技术选型 | 成熟度 | 风险 |
| --- | --- | --- | --- |
| Agent 编排 | LangGraph | 高 | 低 |
| 后端 API | FastAPI | 高 | 低 |
| 前端 | Next.js | 高 | 低 |
| 关系数据库 | PostgreSQL | 高 | 低 |
| 缓存 | Redis | 高 | 低 |
| 向量数据库 | Milvus | 中高 | 中（SaaS 侧运维成本） |
| Embedding/Rerank | BGE 系列 | 高 | 低 |
| **代码执行** | **Docker Sandbox** | **中** | **高（安全隔离）** |

### 3.2 关键技术风险

1. **Docker 沙箱逃逸防护**：用户代码可在沙箱内执行任意命令，SaaS 多租户场景下隔离失败 = 灾难。需 PoC 验证。
2. **9 节点流水线稳定性**：任意节点失败或超时需可恢复，需设计超时、重试、Checkpoint 恢复。
3. **代码生成正确性**：LLM 生成的代码可能无法编译/测试通过，依赖 Testing Agent 的自修复循环兜底，需设最大迭代上限。

### 3.3 PoC 验证清单（正式立项前必须完成）

- [ ] 沙箱内安全执行 Python / Node / Go 代码，尝试逃逸路径，验证隔离有效性
- [ ] 最小流水线（Manager→Planner→Coding→Execution→Testing→Evaluation）端到端跑通「生成一个订单系统」任务
- [ ] SSE 流式推送的性能与断线恢复
- [ ] 单任务 token 消耗实测，用于校准经济模型

## 4. 经济可行性

### 4.1 成本结构

主要成本 = **LLM 推理费用（按量 API）** + 基础设施（GPU 仅用于 embedding/rerank，可选）。国产模型按量计费，无需自建 GPU 集群，属轻资产模式。

### 4.2 单任务 token 估算

| Agent | 调用次数 | 输入 token | 输出 token | 说明 |
| --- | --- | --- | --- | --- |
| Planner | 1 | 3k | 1k | 生成任务图 |
| Research | 1-3 | 5k | 1.5k | RAG 检索 + 上下文 |
| Architect | 1 | 5k | 3k | 系统设计 |
| Coding | 1-5 | 8k | 3k | 自修复循环放大次数 |
| Execution | 0-1 | 1k | 0.5k | 主要走工具 |
| Testing | 1-3 | 6k | 2k | 生成/执行测试 |
| Evaluation | 1-2 | 15k | 1k | 读代码，输入大 |
| Report | 1 | 5k | 2k | 汇总报告 |
| **合计** | **7-17** | **~50k-150k** | **~15k-40k** | |

### 4.3 单任务成本测算

以国产低价模型（DeepSeek / Qwen 档位，具体价格需实测）估算：

- 单任务成本区间约 **¥0.05 - ¥0.5**，取决于任务复杂度与自修复次数
- 必须引入**模型路由**：简单节点（Planner/Research）用低价模型，复杂节点（Architect/Evaluation）用更强模型
- 必须设**任务 token 上限**，防止自修复循环失控

### 4.4 收入模式（建议）

- 订阅制 + **任务信用制**（每任务消耗 N 信用点），防止成本失控
- 示例档位：
  - Free：每月少量任务，引流与体验
  - Pro：每月 100 次任务
  - Team：每月 500 次任务 + 共享项目空间

### 4.5 盈亏平衡

单个付费用户边际成本 = 月任务量 × 单任务成本。定价需覆盖 LLM 成本 + 基础设施 + 合理毛利。模型路由 + 任务限额是保证毛利率的关键机制。

## 5. 运营可行性

- 纯 SaaS 轻运营：无硬件采购、无复杂交付
- 获客渠道：开发者社区、技术博客、SEO、免费档引流
- 需建立：用量监控、成本告警、免费额度滥用防护、多租户资源配额

## 6. 法律与合规可行性

### 6.1 数据安全

- **国产模型为主** → 数据可保持在境内，规避数据出境风险
- BGE embedding 境内部署/调用
- 用户任务数据加密存储、最小化收集

### 6.2 内容合规

- 生成代码的版权与开源许可：通过提示词约束 + 用户协议免责声明
- 明确 AI 生成内容的责任边界（用户协议条款）

### 6.3 隐私

- 账号、任务、代码数据的存储与隐私政策
- 用户可删除自己的任务与知识库数据（符合国内个保法要求）

## 7. 风险分析

| 风险 | 等级 | 应对措施 |
| --- | --- | --- |
| 沙箱逃逸导致多租户安全事故 | 高 | PoC 先行、纵深防御（网络隔离/资源限额/超时/只读）、定期加固 |
| LLM 成本失控 | 高 | 模型路由、任务 token 上限、用量告警、任务信用制 |
| 任务成功率低、用户流失 | 中 | 测试循环兜底、限定 MVP 任务类型、逐步扩大能力 |
| 国产模型复杂任务能力不足 | 中 | LLM 接口层抽象，预留切换/路由能力 |
| 数据合规风险 | 中 | 国产模型 + 境内部署 + 隐私政策 |
| Milvus SaaS 运维成本 | 中 | 托管版或轻量替代（先验证，必要时降级） |

## 8. 立项结论

**可行，建议立项。** 前置条件：

1. 先完成 PoC（沙箱安全 + 最小流水线 + 成本实测）
2. 锁定 MVP 任务类型：Web 应用全栈生成、脚本/工具生成、代码审查
3. 商业化采用「订阅 + 任务信用制」，模型路由作为成本控制核心
4. 首版明确不做企业级功能，作为后续扩展方向
