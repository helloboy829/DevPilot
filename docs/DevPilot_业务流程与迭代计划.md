# DevPilot 业务流程与迭代计划

## 数据构建业务主线

材料批次、逐组件候选、单项目归档、人工审核/冻结、组件适用计划、输入映射和无 expected 执行的唯一详细业务合同见[评测数据构建与执行工作流](DevPilot_评测数据构建工作流.md)。逐条原生响应和效果展示见[效果工作台](DevPilot_效果测试工作台设计.md)，压测 profile/指标见[性能工作台](DevPilot_AI性能测试工作台设计.md)。该业务流程文档不重复数据状态机与当前实现状态；当前进度见[模块进度](DevPilot_实现进度与下一步.md)，当前代码/部署见[交付状态](DevPilot_Delivery_Status.md)。

## 流程增补：先定标准，再执行（2026-11-08）

冻结 QA/请求 → 冻结计划及可选版本化效果阈值 → 独立准入和授权 → 有界采集 → 全样本人工复核 → 精确阈值判定 → 未批准草稿/整改复测 → 后续独立正式审批。

旧探索计划不补写阈值；换门槛必须新计划，不能算同基准复测。复核完整、阈值达标、正式批准是三个状态。模板 1.1.0 固定标准，1.0.0 与旧报告保持原样。[已实现范围和后续缺口](DevPilot_Frozen_Effectiveness_Criteria.md)。

## 2026-11-08 追加：派发日志与执行准入分离

[耐久派发日志](DevPilot_Durable_Dispatch_Journal.md)仅持久记录可能发送的 ordinal、保守预算与技术状态。独立准入必须在将来 Worker 调用之前验证权限/目标/内容和全局资源；冻结计划与日志票据都不是授权。已派发未知请求禁止自动重发；租约过期中断整次运行，不回收槽位继续。技术记录结束仍需输出存证与人工复核，不能进入报告 PASS 分母。

## 报告 Agent 增补（2026-11-07）

报告模块新增可选 Agent 步骤：填报/校验 → 每次授权汇总指标外发 → AI 未核验建议 → 人工审阅并确认附入 → 生成新草稿。确定性普通报告不依赖模型；修改事实/模板/语言使建议失效。附入确认不是审批，I0 安全/耐久执行门禁、平台结果引用和正式报告修订仍是后续优先项，不据此宣布 I1 闭环完成。

## 报告模块最小切片（2026-11-07）

在 I0 门禁修复同时交付低风险、无目标调用的报告草稿入口：人工填报 → 确定性校验 → 选择确切模板版本 → 预览 → Markdown/JSON 下载。该切片没有服务端保存、平台结果接入、审批或 Word/PDF，不能当作 I3 正式报告链路完成。接下来先完善执行安全/耐久性，再做报告事实引用与修订归档；模板管理/正式发布按 [报告设计](DevPilot_报告模块设计.md) 分阶段验收。新模板版本不覆盖历史产物，修改指标使旧审批失效。

> 2026-11-06；目标流程。所有阶段均待对应代码和验收证据，不继承旧 M1–M5 完成状态。

## 2026-11-07 试点校准

提测后先选择摸底 BASELINE 或验收 ACCEPTANCE；无批准标准只能摸底归档，不进入 accepted。目标项目状态增加 baseline_completed（已完成摸底）→ closed 分支；摸底转验收须新建/审批方案。上述为后续开发契约，非现有状态字段。

首个闭环优先选历史问数/问答材料，但先补授权参考源与可复核答案。先人工导入审核数据跑通平台→复核→基础报告，再做自动生成；第二个切片用独立公式结构化任务验证规则/单位/文案分层；预测需要历史真实值，CV 需要额外合法图片/标签。本批材料不能证明 CV 适配已具备。

正式立项前澄清：历史评分是否采用加权口径、成功/全部请求延迟口径、动态源快照、真实负载/写入授权。参见[材料分析](DevPilot_历史材料分析与设计校准.md)。

## 1. 业务阶段与交付件

| 阶段     | 输入                            | 自动化                                   | 人工门禁 / 输出                                       |
| -------- | ------------------------------- | ---------------------------------------- | ----------------------------------------------------- |
| 提测     | 清单、cURL、样例、来源          | 解析/缺项提示/凭据分离                   | 提测方确认；Submission/组件版本                       |
| 接入     | cURL / RequestSpec 和批准目标   | 人/Agent 共用调试，协议/提取/首内容验证  | 工程师确认指定修订/环境；单次脱敏证据，不授予压测许可 |
| 数据     | 历史数据、参考源                | 清洗、切片建议、候选生成/质量检查        | 领域复核；冻结数据与质量卡                            |
| 计划     | 数据、业务标准、负载许可        | 推荐 rubric/指标/负载和成本              | 工程师/审批人；冻结计划                               |
| 交付入口 | 已确认请求、获准数据和冻结方案  | 平台直接测为主；可选组装独立 Python 工程 | 导出审批/脱敏/自检；平台无导出也能完成闭环            |
| 效果     | 快照与有界并发                  | 共享核心调用、规则/裁判、计数            | 待审任务与完整证据                                    |
| 复核     | 数据标签/输出争议/抽检/性能异常 | 建任务、分配、对照、受控重算             | 人工决定/必要仲裁；原证据不变，新 assessment          |
| 性能     | 独立负载方案/时间窗             | warmup/阶梯/采样/聚合                    | 异常时停止；每档指标与瓶颈说明                        |
| 决策     | 完整效果/性能/数据证据          | 确定性门禁与报告草稿                     | 未过→整改；通过→报告审批                              |
| 复测     | 新版本和整改说明                | 同冻结基准重跑、差异分析                 | 部分复测不能全量放行                                  |
| 知识     | 材料/难例/评语                  | 脱敏、归纳、候选经验                     | 审核后发布，评估后推广                                |

**目标项目业务状态机（待开发，不是当前 API/数据库状态）**：draft → preparing → ready → running → reviewing → accepted → closed；reviewing → remediation → preparing 为整改循环。材料/来源不足留 preparing，运行异常转 reviewing 处理，不自动接受。accepted 需报告审批，不因单运行 PASS 自动触发。closed 是归档动作，不能抹去最终 verdict。当前 `evaluation_projects` 只有 ID、owner、名称和创建时间，没有该状态字段或对应转换接口。

**目标计划生命周期（待开发，不是当前计划状态字段）**：draft → in_review → approved → frozen → retired；驳回进入新修订，任何变更均使关联旧审批失效。当前 `evaluation_plans` 保存不可变的 `frozen_definition_only` 定义；创建计划时即写入定义并记录 `plan_frozen`，没有通用编辑、送审、批准或退役状态流。后续实现需将目标审批生命周期建模为显式、可审计的修订/审批资源，不得把当前创建即冻结行为描述成已实现此流程。

## 2. 旧里程碑名称（历史路线，仅作概念映射）

下表保留 2026-11-07 的 I0–I5 里程碑语言，供理解旧文档；它不是当前 backlog、排期或完成状态。当前开发顺序统一由[实现进度](DevPilot_实现进度与下一步.md)维护；新功能细节见[功能实现说明](DevPilot_Feature_Implementation_Spec.md)。

| 迭代                        | 可交付切片                                                                                                                                 | 退出条件                                                                                                                   |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------- |
| I0 可信地基                 | F01–F09、F13–F14、包部署、能力约束/安全/耐久执行                                                                                           | 先失败测试后修复；零/全失败/缺指标不 PASS；Docker import、重启/取消、泄密与限额回归                                        |
| I1a 问答平台闭环            | 项目/提测、cURL 调试/确认、现成数据、冻结计划、双测试、基础复核待办/结果对照、基础报告                                                     | 历史 QA 项目复现；不要求写 JSON/脚本；复核不改原证据；基础整改+全量复测                                                    |
| I1b 独立导出                | 已验证 adapter、共享核心、Python 工程、权限与脱敏                                                                                          | 干净环境安装/自检、假服务等价、一次受控真实运行；可晚于 I1a 单独发布                                                       |
| I2 数据优先自动化（待开发） | 项目外材料批次、清单/附件解析、多组件候选、已有/新项目归档、归档后审核冻结、组件适用计划选数与输入映射、原生响应留存及无 expected 评估路径 | 全清单组件均有完成/阻断/显式排除状态；来源、授权和质量可追溯；无未审候选进入计划；缺 expected 不阻止调用但金标指标不可伪造 |
| I3 CV 与报告                | 先图像分类，再按需检测/OCR；用户报告模板映射                                                                                               | 代表 CV 项目；真实文件/标注切片；模板校验和审批通过                                                                        |
| I4 知识与长期回归           | 历史材料迁移、经验推广、复测对比、通知、回滚                                                                                               | 隔离/删除/污染回归；知识版本变更前后可对照                                                                                 |
| I5 深度自动化               | 多轮 Agent、可选外部压测器、定时评测、有限自动审批                                                                                         | 前几阶段稳定，单独风险审查与负载验证                                                                                       |

I2 是数据构建主线，不另造 Agent Runtime 或第二套 QA runner。先完成受限格式解析、批次与组件映射，再接候选生成、质量门禁、项目归档和审核；随后扩展计划输入映射与基于原生响应的评估。已有冻结版本 ID/revision/hash 继续用于执行快照；阶段状态以当前[交付矩阵](DevPilot_Delivery_Status.md)为准。

## 3. 每个开发切片的工作流

业务验收例 → 契约/API/schema/威胁模型 → 失败测试 → 最小实现 → 单元/集成/界面回归 → 离线历史项目回放 → 人工评审 → 文档/迁移/回退 → 发布。

每项任务包含 owner、需求 ID、修复 ID、代码范围、依赖、测试、验收样例、成本与回退；状态为待办/开发中/待验收/已验收/阻塞，未有证据不得写完成。

## 4. 每轮应看的运营质量指标

数据：有效标签比例、关键切片覆盖、真实/合成比例、标注冲突、泄漏率。
判定：人工一致性、误放行/误拒绝、待审率、裁判不可用率。
流程：材料返工、接入确认后失败率、导出自检/等价通过率、复核待办/逾期/争议率、每条人工时间、完整报告时长、复测可比率。
稳定性：任务中断/恢复、请求错误、发生器瓶颈、预算超限和脱敏失败。

指标只用于发现瓶颈，不把“生成更多用例”当唯一绩效。通过率下降可能是更好覆盖，不自动归咎目标或工具。

## 5. 需要用户提供的试点材料

脱敏清单/报告模板、1 个 QA + 1 个 CV 历史项目、真实 cURL 和成功/错误/流式响应、参考数据授权、人工标签和争议样例、效果门槛、允许并发/时段/成本、整改前后版本。先用小批代表材料校准，不一次导入全部敏感资料，也不把明文 token 放进 Git。

## 6. 自动化逐级开放

- L0：可重复执行；人工导入金标、审批计划/负载，程序跑数和填报告。
- L1：助手检查材料、生成候选、建议规则、解释差异；数据/计划/报告门禁仍由人确认。
- L2：稳定任务使用预批准的模板、冻结数据和负载授权，可自动启动回归/同基准复测；仅异常与抽样复核进入人工队列。

每个自动化授权绑定范围、版本、费用/并发、有效期和撤销人。新任务、新来源、新标签规则、阈值放宽、未批准出站和正式发布不得沿用旧授权绕审。首版不承诺 L3 全无人审核验收；以人工一致性、事故和成本数据决定是否进一步开放。
