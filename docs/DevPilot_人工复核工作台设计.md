## 1. 产品决策：独立中心 + 就地入口，同一套任务

全局“人工复核”解决跨项目待办、分工和进度；数据集/运行结果页提供“复核此条”入口并嵌入相同详情组件。两处引用同一个 ReviewTask、Decision 和 Resolution，不另存两份状态。助手可以整理证据、建议送审，但不能冒充人提交决定。

| 复核种类             | 审核对象                                 | 产出与边界                                                    |
| -------------------- | ---------------------------------------- | ------------------------------------------------------------- |
| dataset_label        | 运行前：输入、预期、标签、来源、rubric   | 审核标签；冻结前修改草稿并重审，冻结后只能新数据版本          |
| case_judgment        | 运行后：原始输出、提取结果、自动裁判     | 新人工决定与解析后的最终 outcome；不改原始观测                |
| measurement_validity | 性能环境、时间线、窗口、错误、发生器异常 | 确认/否定测量有效性，必要时重跑；不可手改 p95/TTFT 或豁免门槛 |

计划、数据版本整体批准和报告签批仍是 Approval 资源，不把“这一条语义 PASS”混成“批准全项目”。标签审核通过也不自动批准整个数据版本。

## 2. 队列：让评测者先知道该看什么

入口：/workspace/evaluation/reviews，默认“分配给我 / 可领取 / 待仲裁”。筛选项目、组件名/版本、task_type、数据/运行、切片、风险、自动建议、送审原因、负责人、时限；权限过滤在服务端完成。

每行最少展示：**组件名与版本、case ID、输入 Q 缩略、输出 A 缩略、预期要点缩略、送审原因、风险、负责人、任务状态**。资料缺失显式标出；点击进入完整上下文，缩略内容不能作为独立裁决依据。预期无查看权限时不返回隐藏字段。
优先级：高风险切片/硬约束争议 → 裁判不可用或不确定 → 自动与规则冲突 → 失败与随机抽检。不是只审核 FAIL；按冻结抽检策略随机抽 PASS 防误放行，记录抽样种子、范围与覆盖，不能由助手挑“容易通过”的样本。
工作量看待办/逾期/争议数、完成覆盖和一致性，不以 PASS 数量考核复核人。

## 3. 详情：一屏对照、证据可定位

```text
顶部：项目 / 组件名与版本 / case / run / 数据与rubric版本 / 风险 / 任务状态
左：输入 Q 与上下文        中：目标输出 A              右：预期与证据
    图片/多轮历史/附件        提取结果/原始响应切换         必需事实/可接受变体/禁项
    输入参数/输入hash         错误/结束原因/截断提示         来源原文、页码/片段、版本
底部：判断维度 / 决定 / 理由与证据 / 暂存 / 提交并下一条
可展开：自动裁判理由、历史决定、Agent轨迹、性能详情、相邻样本
```

- **问答/LLM**：突出用户问题、必要上下文、回答、预期要点、容差/拒答条件、引用片段。可查看差异/高亮，但文本相似度不是正确性证明；长文可搜索/展开，截断需显式提示且不隐藏裁决必需内容。
- **CV 分类/检测**：原图、金标与预测叠加，缩放/平移、类别与置信度筛选、框坐标/IoU 和字典版本；大图受限分辨率预览并允许授权查看原件。不能只让人看 JSON。
- **OCR/结构化**：图像区域、识别文本/字段、期望值和单位/容差对应，不把不同字段混为一个分数。
- **Agent**：完整用户任务、多轮轨迹、工具输入输出、最终回答、已知环境与副作用；仅看最后一句 A 不足以判任务完成。
- **性能**：按档/重复展示窗口、有效请求、失败分布、TTFT 可观测性、负载机状态与原始采样。复核的是证据质量，不给人编辑测量数字。

默认先看事实再看自动建议；高风险双人盲审隐藏自动结论及其他人决定，避免锚定。若业务采用非盲审，记录 policy。可辅助高亮，不自动选中 PASS。

## 4. 动作与判定边界

| kind                 | decision.action                                                  | 后续                                                                        |
| -------------------- | ---------------------------------------------------------------- | --------------------------------------------------------------------------- |
| dataset_label        | approve_label / request_changes / escalate                       | 标签批准；退回新修订；送专家                                                |
| case_judgment        | pass / fail / insufficient_evidence / reference_issue / escalate | 建议 PASS/FAIL；资料不足保持 PENDING/待补证；金标疑错阻断并发起修订；送仲裁 |
| measurement_validity | valid / invalid / insufficient_evidence / escalate               | 记录测量有效性；无效/不足需补证或重跑，不改原采样                           |

每次提交带 subject_revision/hash、task expected_revision、reason_code、说明、evidence_refs；人工 actor 由后端身份确定，不允许客户端填写 reviewer 名字冒充。风险策略可要求逐维 rubric 与理由，拒绝空理由批量盖章。
对技术 ERROR/NOT_RUN，语义 pass/fail 动作服务端拒绝：可以标注故障原因、请求重跑，但不能把没得到有效回答的请求“人工通过”。裁判服务错误但目标有有效输出时，case 是 PENDING，可交给人判；目标输出不能因裁判不可用被误记成目标 ERROR。
“参考答案错”不在复核框里修改冻结 expected 后立即放行；应新建数据/基准版本、重审与重判/重跑，并说明旧运行不可直接比较。

支持暂存、上一条/下一条、提交后定位下一待办、键盘快捷键与焦点管理；快捷键不在输入框内触发，离开有未保存提示。暂存不是提交，不计已复核。
批量仅用于获准低风险、同类且已逐条检查的事项，每条保留理由/actor；高风险、盲审、资料不足不得批量 PASS。操作后可发起“修订决定”，形成新 revision，不物理删除或覆盖旧提交。

## 5. 任务、分配、双审与仲裁

- ReviewTask.status：**queued / in_review / escalated / resolved / cancelled**，与 run.status、case outcome 分离。
- queued：待领取；claim 成功进入 in_review，记录 assignment、有效期和任务 revision；服务端原子领取，过期释放并保留历史。单人任务可回 queued，多人任务不得因一人过期抹去其他人已提交决定。
- 双人策略通过独立 assignment 实现：两位不同 actor 对同一 subject hash 独立提交；未满足人数前不 resolved。自审与角色兼任由项目政策显式决定，Agent 永远不是人工 reviewer。
- 满足人数且可作最终判断时由固定 resolver 形成 Resolution；一致“资料不足”也不能 resolved 为 PASS，任务保持待补证/升级；分歧/升级进入 escalated，授权仲裁人补充理由/证据后 resolved；不可多数表决偷偷掩盖硬约束失败。
- 修订已提交决定/重开任务走显式 reopen，新增决定和 Resolution 版本；并发修改用 expected_revision，旧页面提交返回 409 并保留用户草稿，不后写覆盖先写。
- 被审核对象变化、被撤回或数据版本废弃使旧任务 cancelled 或过时；决定只对原 subject hash 有效，新对象新任务。超时/逾期绝不自动通过。

assignment 的 active/submitted/expired/released 是领取记录状态，不复用任务生命周期。Decision 是不可变提交；Resolution 是策略或仲裁产物，三者不能合并成一个布尔 reviewed 字段。

## 6. 从人工决定到最终结果

原始 Observation、Automatic Judgment、Human Decision 分层保存。Resolver 依据冻结 review policy、全部必需决定与证据门禁，计算 effective case outcome 和新的 **RunAssessmentRevision**（计数、指标、verdict、引用集合）。人工建议不直接 UPDATE 自动裁判行。

例如 N_total=100，原 90 PASS、5 FAIL、5 PENDING：通过率仍 90/100；若人审后其中 3 PASS、2 FAIL，变为 93/100、7 FAIL，分母不变。只抽检 5 条则只对这 5 条产生决定，不能推断所有待审都通过。
抽检任务可能绑定原本 PASS 的样本：任务状态不是 case outcome；原 PASS 保留为 provisional，但在必需抽检完成前 run verdict 至少 NEEDS_REVIEW。硬失败/缺必需证据仍依指标规范优先 FAIL/BLOCKED。抽检改判后按原 N_total 重算。
所有必需复核解决前，不因临时通过率达阈值而 PASS。重算不能补出不存在的性能测量或消除技术错误。

报告引用具体 assessment_revision，不随后台最新结果静默变化；复核变更会标记下游报告/验收需重新确认。已发布报告原件只读，新增修订、撤销/重发并通知；旧审批仍属于旧版本，不能挪给新版本。复核中心不能直接发布报告。

## 7. 权限、敏感内容与审计

- 项目访问、领取复核、查看 expected/来源、查看 raw/敏感数据、仲裁、整库导出分开授权；首版 owner 模式先用单人，团队模式必须先实现角色/assignment 隔离，不能仅靠 UI 按钮。
- reviewer 只获得当前任务所需证据；盲测材料不能整体塞进聊天记忆、公开链接或无权限模型。图像/附件按鉴权受控获取，URL 不带秘密。
- 不可信回答与来源按文本/受限媒体渲染，防 XSS、提示注入和外链自动加载；PDF/HTML/图片处理隔离且有体积限制。
- 记录 claim/访问敏感件/提交/仲裁/reopen/导出/权限变更，保留 actor、时间、subject hash、版本与理由；移除 PII 仍保存必要审计引用。

## 8. 分期与验收例

I1：结果页逐条复核 + 基础“我的待办”列表，同一任务服务；单人、完整 Q/A/expected/来源、理由与新 assessment。I2：跨项目中心、分配、双盲/仲裁、抽样策略与运营指标。I3：CV/OCR 图像与结构化证据增强。

必测：1 PASS+1 PENDING 仍是 1/2 且不放行；资料不足/目标 ERROR 不可人工 PASS；两个 reviewer 并发提交不覆盖；必需抽检未结束不能正式通过；已发布报告不被覆写；屏幕阅读器/键盘可完成复核；大段文本/图像不因缩略误判；原金标错误须新基准；盲审不能读别人决定。
